## 2. Minimum functional requirements

### 2.1 Full CRUD on the entities — Met

Every entity exposes `GET /api/<entity>`, `GET /{id}`, `POST`, `PUT /{id}`, `DELETE /{id}`.

| Entity | Controller | Create | Read | Update | Delete |
|---|---|---|---|---|---|
| Category | `CategoryController` | 201 | 200 | 200 | 204 / 409 if it has courses |
| Instructor | `InstructorController` | 201 | 200 | 200 | 204 / 409 if it teaches courses |
| Tag | `TagController` | 201 | 200 | 200 | 204 (detaches from courses first) |
| Student | `StudentController` | 201 | 200 | 200 | 204 / 409 if it has enrollments or reviews |
| Course | `CourseController` | 201 | 200 | 200 | 204 / 409 if it has enrollments or reviews |
| Enrollment | `EnrollmentController` | 201 | 200 | 200 | 204 |
| Review | `ReviewController` | 201 | 200 | 200 | 204 |

### 2.2 At least 3 custom queries addressing distinct business needs — Met (5)

| # | Business need | Endpoint | Repository method | Technique |
|---|---|---|---|---|
| 1 | Catalogue search by title **and** budget | `GET /api/courses/search?keyword=&maxPrice=` | `CourseRepository.search` | JPQL `LIKE` + range filter, `@Param` |
| 2 | Class roster of a course, cancelled excluded | `GET /api/courses/{id}/students` | `StudentRepository.findStudentsOfCourse` | JPQL `JOIN` on a mapped association |
| 3 | Ranking of the most popular courses | `GET /api/courses/popular?limit=` | `EnrollmentRepository.findMostPopularCourses` | `GROUP BY` + aggregated columns + `Pageable` |
| 4 | Revenue generated by an instructor | `GET /api/instructors/{id}/revenue` | `EnrollmentRepository.sumRevenueByInstructor` | `SUM` + `JOIN` |
| 5 | Average rating of a course | `GET /api/courses/{id}/rating` | `ReviewRepository.findAverageRatingByCourseId` | `AVG` |

Three additional **derived queries** are also exposed: courses of a category, enrollments of a
student, reviews of a course.

### 2.3 Relationships between entities — Met

| Relationship | Type | Owning side / join column |
|---|---|---|
| Category ↔ Course | `@OneToMany` / `@ManyToOne` | `Course.category`, FK `category_id` |
| Instructor ↔ Course | `@OneToMany` / `@ManyToOne` | `Course.instructor`, FK `instructor_id` |
| Course ↔ Tag | `@ManyToMany` | `Course.tags`, join table `course_tags(course_id, tag_id)` |
| Student ↔ Course (via Enrollment) | 2 × `@ManyToOne` + `@UniqueConstraint` | association entity carrying `progress`, `status`, `enrolledAt` |
| Student ↔ Course (via Review) | 2 × `@ManyToOne` + `@UniqueConstraint` | association entity carrying `rating`, `comment`, `createdAt` |

This covers one-to-many, many-to-one, many-to-many, and association entities — the same
relationship types listed in Chapter 3, slides 6–10.

### 2.4 Error handling and data validation — Met

* **Validation:** `@NotBlank`, `@Size`, `@Email`, `@Min`, `@Max`, `@PositiveOrZero`, `@Past`,
  `@NotNull` on entities, triggered by `@Valid`.
* **Error handling:** `exception/GlobalExceptionHandler` (`@RestControllerAdvice`) converts
  exceptions into one JSON shape (`ApiError`) with the right status:
  400 validation/malformed input · 404 unknown id · 409 duplicate or still referenced ·
  422 business rule · 500 unexpected.
* **Business rules in the service layer** (not in controllers): uniqueness, delete protection,
  one enrollment per student per course, frozen cancelled enrollments, review only when enrolled,
  progress 100 ⇒ COMPLETED.

## 6. What was verified, and what was not

**Verified by running the code** (details and full log in `docs/TEST_EVIDENCE.md`):

* `mvn clean test` → 5 tests, 0 failures, on JDK 22 **and** JDK 27.
* The application started against an in-memory H2 database and all **76** scenarios of the
  Postman collection were replayed over real HTTP → **76/76 passed**.

**Not verified / still manual:**

* MySQL itself: the run used H2 (`test` profile). The MySQL configuration is the standard
  Spring Boot one and `createDatabaseIfNotExist=true` creates the schema, but it was not
  executed against a live MySQL server in this environment.
* Postman Runner screenshots: they must come from your own Postman run.
* GitHub publication and the teacher invitation.

## 7. Known limits (safe to say out loud)

* No authentication/authorization (not requested by DS1; Chapter 4+ material).
* No pagination on list endpoints (`findAll`).
* Statistics endpoints return a `Map` with the aggregate values instead of a separate response class.
* "Revenue" is the sum of course prices of non-cancelled enrollments; there is no payment model.
